# Session — 2026-07-26

**Goal:** run the whole pipeline end to end — emit import stubs, build the
PPC library, link the host harness, and get a boot-order import trace out of
the real game.

## Outcome

Got three quarters of the way. Stubs generated (214), library current, host
compiled all 229 targets — then the final link failed with ~20
`duplicate symbol` errors and stopped. Root cause found and fixed, but the
game still has not been run: the fix needs a tool rebuild and a fresh
recompile on the Windows box first.

## What worked

- `xex_info --emit-stubs` produced 214 import stubs; `WoSRecomp/CMakeLists.txt`
  picked them up and reported `WoSRecomp: import stubs present`.
- `build_ppc.sh` correctly reported "ninja: no work to do" — the 192 MB
  library was already current.
- `build_host.sh`'s undefined-symbol extractor did its job *and* was honest
  about it: it reported "No undefined symbols found — the failure is
  something else" and dumped the tail, instead of guessing. That's what made
  the real error visible immediately.

## What didn't work / dead ends

- **The first diagnosis was wrong, and it was wrong in a plausible way.**
  The duplicate symbols looked like the recompiler emitting the same
  function twice, so the theory was that `Recompiler::Analyse`'s `functions`
  vector is never deduplicated. That fact checks out — `recompiler.cpp:254`
  sorts by base and there is no `std::unique`/`erase` anywhere in the file
  — but it isn't the cause. Walking all four sites that append to
  `functions`:
  - `.pdata` records: guarded by `image.symbols.find(BeginAddress)`.
  - the `bl`-target scan: same guard.
  - the linear walk: same guard, plus an `address == base` check.
  - `config.functions`: unguarded, but the config had no duplicate
    addresses.
  Reading `XenonUtils/symbol_table.h` also killed a related theory:
  `SymbolTable::find` uses `equal_range(address)`, so it matches on an
  **exact** address, not containment. Overlapping functions are therefore
  routine in this codebase and don't produce duplicate symbols on their own.
  A dedup pass would have been harmless but would have fixed nothing, and
  would have added permanent drift against upstream for no reason.

- **The real cause was one level up, in file management rather than
  analysis.** `SaveCurrentOutData()` writes `ppc_recomp.{cppFileIndex}.cpp`
  with a monotonically increasing index and hash-compares before rewriting,
  so unchanged chunks don't force a recompile. Nothing deletes. Any run that
  produced fewer chunks than the one before left the previous run's *tail*
  sitting in `WoSRecompLib/ppc/`, containing the same functions under the
  old boundaries. `.194.cpp` was this run's last chunk; `.197.cpp` was a
  leftover.

- **The clue that should have been read first was the address clustering.**
  All the duplicates sat in `0x82BD6F50..0x82BD7050` — the very top of
  `.text` (which ends at `0x82BDC9AC`). Chunks are emitted in ascending base
  order, so leftovers *always* hold the highest addresses. A duplicate
  caused by a genuine analysis bug would have been scattered. Reasoning from
  the distribution would have been faster than reasoning from the mechanism.

## Ruled out (with reasoning)

- **Deduplicating `functions` in the recompiler.** Correct-sounding, and it
  would have silenced the symptom, but the duplicates were never in that
  vector. Rejected to avoid a patch hunk that doesn't earn its drift risk.
- **`rm -rf WoSRecompLib/ppc/*` at the top of `recompile.sh`.** Simple and
  certainly correct, but it throws away upstream's hash-compare
  optimisation: every one of the ~200 TUs would recompile on every config
  tweak. The C++ prune keeps incrementality and removes only what's actually
  stale.
- **Splitting the fix into `0002-*.patch`.** `check_patch_drift` compares
  `cat patches/<sub>/*.patch` against the submodule's whole `git diff HEAD`.
  Two patches touching the same file cannot concatenate into that. Kept as
  one file, renamed to `0001-wos-recompiler-fixes.patch` to stop the name
  lying about the contents.

## Addendum — second attempt, same day

- **The fix didn't run.** `build_tools.sh` aborted at
  `patch does not apply and is not already applied`, so XenonRecomp was
  never rebuilt; steps 3–5 all used the old binary and the link failed byte
  for byte identically.
- **The patching mechanism had a latent design flaw**, not a one-off. Per
  patch file it asked: does it reverse (applied), does it apply (not yet),
  neither (fatal). Amending an already-applied patch file lands in the third
  bucket permanently — old hunks block forward, new hunks block reverse.
  Every future amendment of a patch would have done this. Rewritten to
  target the exact state instead: match → skip, clean → apply, mismatched →
  save the diff to `logs/` and reset the affected files, then apply.
  Reproduced the exact broken state locally, confirmed both old checks fail
  on it, confirmed the new path lands on a byte-exact match.
- **The stale-file diagnosis is now confirmed, and by arithmetic rather than
  inference.** The progress line `0.0019879923` at `i = 0` gives
  `functions.size() = 50302`; at 256 per chunk that's 197 files; 199 were on
  disk; `.197` and `.198` are leftovers, and `.197` is exactly what the
  linker named. Both prior "unverified claims" below are now settled.
- **The contiguity check I added was worthless.** Leftovers are contiguous
  by construction — both runs number from zero, so strays are the tail of an
  unbroken sequence and there is no gap to find. It ran and passed while two
  stale files sat there. This is the second time in one day that a check
  looked reassuring and tested nothing (the first: a static library build
  proving nothing about duplicate symbols). Replaced with a comparison
  against a count the recompiler now prints, which also warns loudly when
  that line is missing — i.e. when the tool predates the patch, exactly the
  situation this session was in.

## Addendum 2 — it linked, and it ran

- Deleting `ppc_recomp.197.cpp` and `.198.cpp` produced exactly the
  predicted 198 sources and linked on the first attempt. `WoSRecomp.exe`
  then ran, mapped all 12 sections, and segfaulted before reaching a single
  import stub.
- **A diagnostic trap worth remembering: buffered stdout makes the visible
  stopping point a lie.** Under MinTTY a native `.exe` writes to a pipe, so
  the CRT fully buffers. The tail of the output is lost on a crash and the
  last visible line is wherever the buffer last flushed. Worse, the observed
  output is *self-contradictory* — only ~870 bytes had been written, well
  under the 4 KiB buffer, so under full buffering none of it should have
  appeared. Rather than build a theory on that, the fix is to remove the
  variable: `setvbuf(stdout, nullptr, _IONBF, 0)`.
- The repo had already learned a version of this lesson once (the note in
  `run_logged.sh` about `stdbuf` being useless against a native `.exe`,
  since it works via `LD_PRELOAD`). Same root cause, different symptom, and
  it still cost a round.
- Deliberately did **not** guess at the crash site. The candidates were the
  indirect-call-table commit, the table population loop, or the recompiled
  entry point itself, and the arithmetic said all three should be in
  bounds — table writes land at `[base+0x83000000, base+0x842585C8)`, which
  is exactly the committed range. Guessing further without trustworthy
  output would have burned another round; instrumenting settles it in one.

## Addendum 3 — the crash reporter paid for itself immediately

- It fired on the first try and answered the question in one run: a **read**,
  at an address **below** the guest base, therefore **outside the
  reservation** — which the reporter explicitly labels as host-side rather
  than the game touching bad memory. Combined with the "committing
  indirect-call table" marker never printing, that pinned it to the memcpy
  *source* in the section-mapping loop, on a section after `.XBLD`.
- Worth noting how much the classification did. "Segmentation fault" alone
  had three plausible causes (call-table commit, table population, or the
  recompiled entry point). Read-vs-write eliminated the two write paths;
  inside-vs-outside-the-reservation eliminated the game entirely.
- **Root cause is upstream and structural**, not a one-off: `Image::Map`
  takes `image.data.get() + VirtualAddress` unchecked, and for
  `XEX_COMPRESSION_BASIC` the buffer is sized by summing compression blocks
  while `image.size` is separately assigned the header's `imageSize`. Nothing
  makes those agree.
- Deliberately fixed this in **the harness rather than as a submodule
  patch**. The harness is ours and the validation belongs there anyway
  (it should not trust a loader's pointers), whereas patching XenonUtils
  would add permanent drift for something that hasn't actually broken the
  recompiler. Noted in the findings log that the recompiler reads through
  the same pointers and is fine only by luck.
- The unbuffered-stdout change was load-bearing here. With the old buffering
  the phase markers would have been unreliable, and "which loop iteration"
  was exactly the question that mattered.

## Ruled out this round

- **A page-fault handler that commits guest memory on demand.** It would let
  the game run much further — the harness only commits sections, the call
  table and a 256 KiB scratch stack, so any real allocation faults. But for
  a *first* bring-up run, knowing precisely where and why it stops is worth
  more than getting further with the reason hidden. Worth revisiting once
  the first fault is understood.
- **Reasoning about the crash from the existing output.** See above: the
  output is not trustworthy enough to support a conclusion.

## Unverified claims

- **The prune loop is verified; the prune *in situ* is not.** The loop was
  lifted verbatim into a standalone program and run against a directory
  holding `ppc_recomp.0..5.cpp` with `cppFileIndex = 3`: it deleted 3, 4 and
  5, left 0–2, and on a second run terminated immediately having deleted
  nothing. XenonRecomp itself compiles and links with the patch, and the
  drift check reproduces the patch byte for byte. What is *not* tested is
  the value of `cppFileIndex` at the call site — there's no XEX in this
  sandbox to run a real recompile against. It should equal the number of
  chunks written (`SaveCurrentOutData()` increments only on unnamed saves,
  and the final flush happens before the prune), but that's read from the
  code, not measured. First Windows run should print
  `Removed stale output file from a previous run: ppc_recomp.N.cpp` lines;
  if it prints none and the link still fails, the diagnosis is wrong.
  `recompile.sh`'s contiguity check is the backstop if the count is off.
- **The claim that `.194` was the current tail and `.197` a leftover is
  inference, not measurement.** It fits the addresses and the mechanism, but
  the actual chunk count of that run wasn't recorded.
  **RESOLVED (addendum 1):** measured — 197 chunks vs 199 files, and
  deleting `.197`/`.198` linked first try.
- **The crash reporter and the unbuffered-output fix are compile-verified
  only.** Both platforms type-check (clang on Linux, `x86_64-w64-mingw32`
  for the Win32 path), but there is no Wine in the sandbox, so the handler
  has never actually caught an exception. Specifically untested: whether
  `SetUnhandledExceptionFilter` fires at all under Git Bash, and whether
  `printf` from inside the filter reaches the terminal. If the next run
  still prints a bare `Segmentation fault` with no `=== CRASH ===` block,
  the filter is not being invoked and the fallback is a debugger.
  **RESOLVED (addendum 3):** it fired, printed, and classified correctly.
- **The section-validation change is unit-tested but not run against the
  real XEX.** `CleanName` and the clamp arithmetic have direct assertions,
  and both builds type-check, but which section is actually out of range —
  and whether zero-filling it is survivable — is unknown until it runs. The
  specific prediction to check against: a 13th section, listed after
  `.XBLD`, reported as ZERO-FILLED or CLAMPED. If instead all sections come
  back `ok` and it still crashes in the same place, the diagnosis is wrong
  and the fault is somewhere else in that loop.
