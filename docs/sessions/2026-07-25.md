# Session — 2026-07-25

**Goal:** Go from an empty repo to a working scaffold + toolchain, ready to
ingest a real *Web of Shadows* XEX.

## Outcome

Met, minus the actual game data. Repo scaffolded (structure modelled on
Unleashed Recompiled), both upstream recompilers imported as submodules and
**built and run successfully**, two extra tools added (`xex_info`,
`extract-xiso`), and `import_dump.sh` written to ingest a dump. No WoS
binary in hand yet — user was extracting their disc during the session and
hit a platform detour (macOS, no Homebrew → Docker).

## What worked

- `tools/build_tools.sh` builds all five tools on Ubuntu 24.04 / Clang
  18.1.3 / CMake 3.28. All print correct usage output.
- `tools/xex_info` — our own diagnostic; reuses XenonUtils'
  `Image::ParseImage`, which handles XEX decrypt/decompress automatically
  via magic-byte dispatch.
- `tools/import_dump.sh` — tested against synthetic fixtures: flat
  XISO-style layout, nested GOD-style layout, truncated XEX, and a
  no-XEX-found folder. All four behaved correctly.
- `extract-xiso` vendored after checking its license (modified BSD —
  permissive, fine to bundle).

## What didn't work / dead ends

- **`git submodule add` doesn't recurse.** Adding `tools/XenonRecomp` and
  `tools/XenosRecomp` left all their `thirdparty/` deps (fmt, tomlplusplus,
  xxHash, simde, zstd, dxc-bin…) uncloned; first CMake configure died on
  missing `CMakeLists.txt`. Fix: `git submodule update --init --recursive`.
  The docs already told *users* to do this — the scaffolding step itself
  just skipped it.
- **Tried wiring `xex_info` into the root `CMakeLists.txt`** so it could
  link the `XenonUtils` target from `tools/XenonRecomp`. Doesn't work:
  `build_tools.sh` configures each submodule as an independent project in
  its own build tree, so there's no shared configure to hang a target off,
  and adding both in one configure collides on `XenonUtils` already being
  defined. Reverted; made `xex_info` a standalone CMake project that pulls
  XenonUtils' *sources* in directly instead.
- **`xex_info` segfaulted on a truncated XEX.** Root cause is upstream: the
  XEX loader trusts header-declared offsets/counts without bounds-checking
  them against actual file size. Added validation of `headerSize`,
  `securityOffset`, and `headerCount` in `xex_info/main.cpp` before calling
  into the upstream parser. Note this is *our* guard — the same latent
  crash still exists in `XenonAnalyse`/`XenonRecomp` if fed a bad file.
- **`.gitignore` bug, pre-existing since the initial scaffold.** A blanket
  `private/` pattern silently defeated its own `!private/README.md`
  negation (git can't re-include a file inside a directory excluded by a
  `dir/` pattern — needs `dir/*`). Result: `private/README.md` had never
  actually been committed despite being linked throughout the docs. Fixed
  to `private/*`; verified game files are still correctly excluded.
- **Couldn't build/test the Docker image here.** Got `dockerd` itself
  running in the sandbox, but the egress policy 403s Docker Hub's CDN
  (`production.cloudfront.docker.com`, confirmed via the proxy status
  endpoint). Policy denial, not a bug — not routed around.
- **WSL2 on the user's Windows box had no outbound network.** `apt update`
  failed against every archive.ubuntu.com mirror. Diagnostically: DNS
  *worked* (names resolved to real IPs like 185.125.190.83), IPv6 returned
  "Network is unreachable", IPv4 returned "connection timed out" — and
  Windows itself had connectivity (the distro image downloaded fine via
  `wsl --install`). So: WSL-specific config, packets leaving but nothing
  returning, which typically means firewall/AV or VPN interference with
  the Hyper-V virtual adapter. **Not diagnosed further** — pivoted to
  native Windows instead rather than sink time in it. Standard fixes if
  anyone revisits: `wsl --shutdown`, then `%UserProfile%\.wslconfig` with
  `[wsl2]` / `networkingMode=mirrored`.
- **First real Windows build failed at CMake configure.** Environment was
  VS 2026 (v18.8.1), **Clang 22.1.3**, CMake 4.3.1, Ninja 1.13.2 — all far
  newer than the Linux reference (Clang 18 / CMake 3.28). Error:
  `MSVC_DEBUG_INFORMATION_FORMAT value 'ProgramDatabase' not known for this
  C compiler`, from `CMakeTestCCompiler.cmake` at the compiler-check stage.
  Cause: XenonRecomp's `CMakeLists.txt:10` sets
  `CMAKE_MSVC_DEBUG_INFORMATION_FORMAT` under policy CMP0141, and also sets
  `CMAKE_MSVC_RUNTIME_LIBRARY` — both MSVC-ABI abstractions. CMake had
  selected `clang.exe`, reported as *"Clang 22.1.3 with GNU-like
  command-line"*, and the GNU-style driver doesn't implement them. **Not a
  version problem** — Clang 22 is fine; it's the *driver* that was wrong.
  Fix: prefer `clang-cl.exe` (same compiler, MSVC-compatible driver, ships
  alongside in VS) on Windows. `build_tools.sh` now selects it
  automatically.
- **Second Windows failure: archiver/driver mismatch.** After clang-cl fixed
  the configure stage, the build reached 23/34 objects then died linking
  `disasm.lib`:
  `llvm-ar.exe: error: unknown option /`. CMake had emitted the MSVC
  archive rule (`<CMAKE_AR> /nologo /out:<TARGET> <OBJECTS>`) but
  autodetected `CMAKE_AR` as **`llvm-ar.exe`**, the GNU-style archiver,
  which only accepts `-`-prefixed flags. LLVM ships both: `llvm-ar` (GNU,
  pairs with `clang.exe`) and `llvm-lib` (MSVC-compatible, pairs with
  `clang-cl.exe`). Lesson worth generalising: **picking the MSVC-style
  compiler driver isn't enough — every tool in the chain has to match the
  flag convention.** Fixed by pinning `CMAKE_AR` to the `llvm-lib.exe`
  adjacent to whichever `clang-cl` is on PATH. Verified the detection
  logic and its not-found fallback against a mock LLVM bin directory,
  and confirmed the change is a no-op on Linux (CMAKE_AR there still
  autodetects `llvm-ar-18`, correctly, since the driver is GNU-style).
- **`build_one` was hiding CMake errors.** It attempted the Ninja generator
  with `2>/dev/null` and retried with the default generator on failure —
  so the first configure's real error was swallowed and every configure
  appeared to run *twice*. Visible in the user's failure output. Replaced
  with an explicit up-front `command -v ninja` check. Also added a
  `CMAKE_ARGS` passthrough (verified it reaches the cache) after nearly
  documenting it as an escape hatch that didn't exist.
- **`build_tools.sh` had two latent Windows bugs**, found by reading it
  against the Git Bash environment rather than by running it: (a) job count
  came from `nproc`, which Git Bash doesn't have, so it would silently fall
  back to 4 jobs on a 32-thread machine; (b) if `clang-18` wasn't found it
  fell back to plain `clang` with no version check, so an ancient Clang
  would be used silently and fail confusingly much later. Fixed both —
  `NUMBER_OF_PROCESSORS`/`sysctl` fallbacks for core count, and a hard
  error below Clang 18.

- **Third Windows failure was the *same* bug, not a new one.** After
  pinning `CMAKE_AR=llvm-lib.exe`, the build printed the correct archiver
  and *still* invoked `llvm-ar`, failing identically. The `-D` flag wasn't
  at fault: a CMake build tree pins its toolchain at the **first**
  configure, and the generated `CMakeFiles/<ver>/CMakeCCompiler.cmake` does
  a plain `set(CMAKE_AR ...)` that is re-included on every reconfigure,
  shadowing the command line. The build dir predated the fix, so it kept
  the old archiver while *appearing* to accept the new flag. Tell:
  `Configuring done (0.2s)` — a cached no-op. Fixed by comparing the
  cache's `CMAKE_C_COMPILER`/`CMAKE_AR` against what the run intends and
  wiping the tree on mismatch (`CLEAN=1` forces it).
  **Generalisable:** a passed flag that gets *printed* is not evidence it
  was *applied*; with CMake, verify against the build tree's own state.
- **My own verification of that fix was initially bogus.** The test
  injected a foreign compiler via `sed` on `CMAKE_C_COMPILER:FILEPATH=`,
  but the real cache line is `:STRING=`, so the substitution silently
  matched nothing and the test "passed" without exercising the code path.
  Caught and re-run properly. Lesson: a passing test that never ran its
  target is worse than no test.

## Ruled out (with reasoning)

- **Using the existing PC port as recompiler input.** Wrong binary
  entirely: XenonRecomp consumes the Xbox 360 PPC `default.xex`. The PC
  build is x86 and cannot be fed to it. *However* — see Open threads — the
  PC build is likely valuable as **reverse-engineering reference**, which
  is a different use and was initially under-sold.
- **A full VM for isolation.** Overkill for the actual risk profile (no
  root needed, no untrusted code executed — the tools translate PPC to C++
  source, they don't run the game). Docker recommended instead when the
  user turned out to have no Homebrew.
- **Flipping XenonRecomp's optimization flags** (`skip_lr`, `*_as_local`,
  etc.) early. All left `false`. Turning them on before there's a working
  build makes miscompiles far harder to diagnose.
